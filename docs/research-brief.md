# Research brief: AI document parsing for antitrust-discovery documents (Nov 2026)

Produced by a research subagent on 2026-11-08 for the "document parser" resume project. Vendor accuracy claims are noted as such; several items could not be verified (listed at the end).

## 1. How production parsing pipelines look today

The dominant production shape in 2025–26 is **hybrid, region-routed, and grounded**, not "throw the page at a frontier VLM." Reducto's publicly described pipeline (1B+ docs processed) is the clearest template: layout detection first (in-house autoregressive layout models for dense pages, cheaper detectors otherwise) → **per-region complexity routing** → classic OCR for clean text, in-house VLMs for handwriting/stamps/watermarks/vertical text, dedicated table models (HTML/Markdown/JSON out), an agentic multi-VLM chart extractor → pixel-level grounding map for citations and confidence → downstream Extract/Classify/Split. Embedded PDF text is used directly when the text layer is trustworthy, because it's both cheaper and more accurate than vision for digital-native pages. For long documents Reducto recommends parsing to text first rather than feeding hundreds of page images; text input handles 100+ pages and 100+ fields in one shot, while image input hallucinates more at scale ([ZenML case study](https://www.zenml.io/llmops-database/production-scale-document-parsing-with-vision-language-models-and-specialized-ocr)).

The same stage list (ingest → render → OCR/layout → classify/split → schema extract → validate → human review) appears in LlamaParse/LlamaExtract, Extend, Nutrient, Azure Document Intelligence, Textract and Google Document AI; the vendors differ mainly in how much of the OCR stage is a VLM. Mistral OCR 3 (Dec 2025, `mistral-ocr-2512`, $2/1k pages, $1 batch) is a VLM-style OCR that outputs Markdown + HTML tables ([PyImageSearch](https://pyimagesearch.com/2025/12/23/mistral-ocr-3-technical-review-sota-document-parsing-at-commodity-pricing/)); Docling, Marker/Datalab, Chunkr and olmOCR-2/DeepSeek-OCR/PaddleOCR-VL are open-source alternatives. Thoughtworks put "VLMs for end-to-end document parsing" in **Assess** (Apr 2026): simpler architecture, but "prone to hallucinations," and "use cases with a low tolerance for error may still need a hybrid approach or deterministic OCR" ([Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/vision-language-models-for-end-to-end-document-parsing)).

**OCR-first vs. VLM end-to-end, current evidence:**

- **ParseBench** (LlamaIndex, Apr 2026, ~2,000 pages; vendor-authored, so discount LlamaParse's win): VLMs (Gemini 3 Flash, GPT-5 Mini, Haiku 4.5, Qwen3-VL, Dots OCR) score well on content faithfulness (86–90%) but near zero on charts and **<7% on visual grounding**; specialized parsers (Azure 73.8%, Textract 70.4%) win grounding but lose on charts/semantic formatting. Gemini 3 Flash ~0.65¢/page; paying more (Opus, Gemini Pro) did not reliably improve scores ([arXiv 2604.08538](https://arxiv.org/pdf/2604.08538)).
- **DISCO benchmark** (early 2026): OCR-first wins on long/multi-page, text-heavy docs (DUDE 0.514 vs 0.493 direct VLM); direct VLM wins on single-page/visually dense docs (DocVQA 0.908 vs 0.876). OCR-first is also the best cost/accuracy choice when you ask multiple questions of the same document, since you pay OCR once ([arXiv 2603.23511](https://arxiv.org/html/2603.23511v1)).
- Reducto's own tests show VLM-OCR failure modes to expect on scans: repeated/duplicated table blocks, dropped headers/footers, misread IDs ("JZP-110" → "I2P-110"), checkbox flips ([Reducto](https://reducto.ai/blog/lvm-ocr-accuracy-mistral-gemini)). Vendor benchmarks diverge wildly from each other (Mistral claimed 94.9% vs Reducto measuring 45.3% on forms), so **trust only your own eval set**.

Consensus, such as it is: *OCR/layout first for text-heavy, multi-page, and anything you must cite; VLM direct for single messy pages, handwriting, stamps, charts; always keep page/bbox provenance.*

## 2. Structured extraction patterns

The commercial APIs have converged on a common contract: JSON Schema in → data + a **parallel metadata tree** out. Extend returns per field `logprobsConfidence` and `ocrConfidence` (0–1) plus, with citations on, page dimensions, polygon coords and the matched source text ([Extend docs](https://docs.extend.ai/extraction/overview)). Nutrient mirrors `output.data` with `output.metadata` carrying match label (exact/fuzzy/not_found), page, bbox, confidence, and recommends a starting policy of ≥0.90 auto-accept, 0.70–0.89 warn/review, <0.70 reject, calibrated per doc type; route `fuzzy_match`/`not_found`/missing-citation-on-required-field to human review; validate with AJV even when using strict mode; retry only transient HTTP errors, never 4xx ([Nutrient guide](https://www.nutrient.io/guides/dws-data-extraction/extract/production-structured-extraction/)). LlamaExtract v2.5 (Oct 2026) is "agentic": adapts effort to layout, uses intermediate representations for long lists, validates against the schema, keeps cross-page records together, and its "Advanced Citations" grounding score jumped from ~47 to ~81 on their ExtractBench; value F1 93.9–96.4 across tiers ([LlamaIndex](https://www.llamaindex.ai/blog/introducing-extract-v2-5)).

Practical patterns for this stack: generate structured output via the AI SDK (`generateObject`/`Output.object` with Zod), then run a **validate → feed Zod errors back → regenerate (bounded, 1–2 tries)** loop; make every scalar field `{value, confidence, page, bbox?, source_text}`; chunk by page but extract header/metadata fields from page 1 (+last page for emails/memos) and let a whole-doc text pass fill the rest; prefer text-layer input when `pdf.js` reports real text, else render at 150–200 DPI and OCR. Gemini's native PDF ingestion is the main "skip the renderer" option (docs page could not be fetched; from memory each page costs ~258 tokens and large docs go through the Files API — verify current limits).

## 3. Model routing / cascades

FrugalGPT (2023) set the reference claim: match GPT-4 with up to 98% cost reduction via a cascade with a learned scorer ([arXiv](https://arxiv.org/abs/2305.05176v1)). The 2026 picture is more sober. **LLMRouterBench** (400K instances, 33 models, 10 routers) finds the best routers give ~4% accuracy gain or **up to 31.7% cost reduction at Best-Single-Model accuracy**; binary cascades (HybridLLM, FrugalGPT) struggle to save cost without losing accuracy, several routers don't beat the best single model, and **OpenRouter's commercial auto-router was the worst tested (−24.7% vs best single)** ([arXiv 2601.07206](https://arxiv.org/html/2601.07206)). Document pipelines in practice route on *document signals* rather than learned routers: Reducto routes per region by complexity; Nutrient's `auto` parse mode routes per page. The credible pattern: a **deterministic cascade**: text-layer present → cheap text model; scan with high OCR confidence → cheap VLM; schema validation fails, required-field confidence below threshold, or critical-field cross-checks fail (e.g., totals don't sum) → escalate to a stronger model; still failing → human queue. Log cost per document per tier to report real savings.

## 4. Evals for document extraction

Braintrust's Oct 2026 guidance is the best concise reference: **one scorer per field type**, not a blended accuracy. Levenshtein/embedding/LLM-judge for names and free text; normalize dates to ISO before comparing and fail ambiguous day/month rather than guess; strip formatting and require exact decimal equality on money; preserve case and leading zeros on identifiers (Bates numbers!); check enums against the allowed set and separate "schema violation" from "valid-but-wrong." Treat null-vs-null as correct, omitted and **invented** values as distinct failure classes, and make document acceptance a separate gate requiring all critical fields to pass ([Braintrust](https://www.braintrust.dev/articles/how-to-score-individual-fields-in-llm-document-extraction)). Public benchmarks for context: **OmniDocBench** (text edit distance + table TEDS + formula CDM; top composite ~94.6 GLM-OCR, Gemini 3 Pro 90.3) ([CodeSOTA](https://www.codesota.com/ocr/benchmark/omnidocbench)), **olmOCR-bench** (7,010 unit tests over 1,402 PDFs incl. old scans; infinity-parser2-pro 87.6, chandra-2 85.9) ([CodeSOTA](https://www.codesota.com/benchmark/olmocr-bench)), **ParseBench** (adds grounding and charts), plus the older DocVQA/DUDE. Tooling: Langfuse is MIT/self-hostable with a 50k-unit free tier; Braintrust is proprietary with GitHub-Action PR gating (1 GB free) ([Braintrust comparison](https://www.braintrust.dev/articles/langfuse-vs-braintrust)); promptfoo is fine for CLI/CI regression. Credible portfolio metrics: per-field exact/normalized accuracy, invented-value rate, document pass rate, **grounding accuracy (page correct; bbox IoU if you have boxes)**, cost/page and p50 latency per tier, plus a confusion matrix for doc-type classification.

## 5. Legal / e-discovery specifics

Relativity aiR (standard in RelativityOne for 2026) does GenAI first-pass **responsiveness/issue coding** with per-document rationale ("90%+ recall" claimed, "up to 3M docs/day", "10–20% more relevant docs than TAR"), and **aiR for Privilege** takes Known Attorneys/Known Law Firms lists plus a layered "Brain" of prior decisions, and outputs a privilege call, a rationale citing snippets, and "20+ data points" that feed priv-log creation; requires extracted text ≤170KB/doc ([Relativity help](https://help.relativity.com/RelativityOne/Content/Relativity/aiR_for_Privilege/aiR_for_Privilege.htm), [Relativity blog](https://relativity.com/blog/air-in-motion-building-on-breakthroughs-to-power-whats-next/)). Everlaw Coding Suggestions returns Yes/Soft Yes/No/Soft No with written rationale and a link to the supporting passage ([Everlaw](https://everlaw.com/product/everlaw-ai/coding-suggestions)). DISCO Cecilia offers cited Q&A, doc summaries, timelines, deposition summaries and Auto Review ([DISCO](https://csdisco.com/offerings/cecilia)). Harvey's Vault "review tables" are schema-column extraction over document sets rather than e-discovery proper ([Harvey](https://www.harvey.ai/blog/the-brief-march-2026)). All accuracy figures above are vendor claims.

**Load-file schema** (FTC Bureau of Competition production guide, Concordance-style DAT with þ/ASCII-020 delimiters): BEGBATES, ENDBATES, PGCOUNT, CUSTODIAN; email: FROM, RECIPIENT(TO), CC, BCC, DATESENT/TIMESENT, DATERCVD/TIMERCVD, SUBJECT, ATTACHMENTID, MESSAGEID, FILEPATH; edocs: PARENTID, CREATEDATE/TIME, MODDATE/TIME, FILESIZE, FILENAME, NATIVELINK, HASH; dates and times in separate fields; Bates zero-padded, no space after prefix, attachments numbered after parent ([FTC guide](https://www.ftc.gov/sites/default/files/attachments/bc-production-guide/bcproductionguide.pdf)). Logikcull's mapping adds BegFamily/EndFamily, BegAttach/EndAttach, FamilyID, ThreadID, Document Date, File Author/Title ([Logikcull docs](https://docs.revealdata.com/logikcull/docs/mapping-load-file-fields-to-logikcull)). A realistic extraction schema is therefore: doc_type, bates_begin/end, page_count, custodian (often not in-document), author/from, to, cc, bcc, date (ISO) + time, subject/title, parent/attachment relations, plus doc-type-specific blocks (financial statement: entity, period, currency, line items; memo: re-line, distribution list) and privilege signals (attorney names, "privileged & confidential" legends).

## 6. Public sample documents

- **DOJ ATR trial exhibit pages**: *US v. Google (2020, search)* ~224 exhibits, mostly emails with attachments plus decks, chats, a financial report, with UPX/PSX/DX numbering and redaction tags ([DOJ 2020](https://www.justice.gov/atr/us-and-plaintiff-states-v-google-llc-2020-trial-exhibits)); *US v. Google (2023, ad tech)* 264 admitted exhibits incl. spreadsheets and third-party docs ([DOJ 2023](https://www.justice.gov/atr/us-and-plaintiff-states-v-google-llc-2023-trial-exhibits)). Public court records; no stated license. Epic v. Apple and FTC v. Meta exhibits exist via PACER/press but were not verified.
- **Enron corpus**: FERC public release, CMU-cleaned, free to use; attachments stripped, 2001-era, and e-discovery practitioners now consider it stale and over-familiar ([EDRM](https://edrm.net/2025/08/still-on-dial-up-why-its-time-to-retire-the-enron-email-corpus/)). Still the best source of real email-header metadata.
- **UCSF Industry Documents Library**: the only large public corpus with real Bates numbers, custodian-like metadata and poor scans; full dataset (files + OCR text + metadata, monthly updates) is on AWS Open Data at `s3://ucsf-idl-dataset` ([AWS registry](https://registry.opendata.aws/idl/)); check UCSF's copyright page before redistributing.
- **EDGAR** gives clean financial statements but no scan noise; degrade them yourself (print → scan → skew) for test data.

## Implications for this project

1. **Build the hybrid, not the VLM monolith**: detect text layer → use it; otherwise render pages and run OCR (Mistral OCR 3 or a local olmOCR/Tesseract baseline) *and* keep the page image available for a VLM pass on low-confidence regions.
2. **Make provenance a first-class type**: every field is `{value, confidence, page, bbox?, source_text}`; render a "click field → highlighted page" view. ParseBench shows this is exactly where raw VLMs fail, so it's a differentiator.
3. **Schema = load-file fields**: adopt the FTC/Concordance vocabulary (BEGBATES…MESSAGEID, PARENTID/FamilyID) and emit a DAT export; reviewers will recognize it instantly.
4. **Deterministic cascade with logged tiers**: cheap text/VLM model → escalate on Zod failure, low critical-field confidence, or failed cross-checks → human review queue in Postgres. Report measured cost/page per tier; don't rely on OpenRouter's auto-router.
5. **Bounded repair loop**: validate with Zod, feed errors back once or twice, then escalate; never retry 4xx-style semantic failures blindly.
6. **Per-field scorers in the eval harness**: normalized dates, exact decimals, case/leading-zero-preserving Bates, enum checks, LLM-judge only for summaries; track omitted vs. invented separately and gate on critical-field pass rate.
7. **Add grounding and classification metrics**: page-hit rate, bbox IoU where you have boxes, doc-type confusion matrix; these are the numbers vendors are now publishing.
8. **Seed the 25-doc ground truth from DOJ Google exhibits + UCSF IDL scans + a few degraded EDGAR statements**; store source URLs and note that court exhibits are public record while IDL has UCSF copyright terms.
9. **Run evals in CI** (Langfuse self-hosted or promptfoo), with a baseline run checked in so regressions show as a diff.
10. **Be honest in the README about vendor numbers**: cite benchmarks, show your own, and note that published OCR accuracy claims disagree by 40+ points across evaluators.
